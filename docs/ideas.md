# Clover Member Assistant - Product Ideas and Priority Groups

> Input to `claude/srs.md`. Not the SRS itself. Every item here becomes an FR, an NFR, a non-goal, or a roadmap line.
>
> Scoped by feature. For the same scope cut by **call driver** - the unit the success metric is actually measured in - see [`call-drivers.md`](./call-drivers.md), which supersedes P1-10 and restructures P1-11.
>
> **Status:** draft, round 3 of brainstorming complete. Reconciled against `case-study-prompt.pdf`. **Date:** 2026-09-07.

---

## 1. Frame

**Problem.** Clover Health's customer service team takes too many calls. Most of them are members asking how their own plan works, which is information that already exists in public plan documents they cannot find or cannot read.

**Success metric.** Reduce the number of calls to customer service. Single metric. Deflection by volume, not handle time.

**Audience.** Clover Medicare Advantage members, mostly 65+. 76% of 65+ own a smartphone. 46% of adults 50+ report little or no trust in AI. Both numbers shape the build more than any technical choice does.

**Channel.** Web chat embedded on cloverhealth.com. One channel. Phone/IVR, SMS, and agent-assist are out of scope for this product, not deferred.

**What it is not.** Not a coverage-determination tool. Not clinical advice. It informs, it does not adjudicate. This boundary is a legal requirement (CMS-4201-F and the Feb 2024 FAQ: AI may assist but must not make coverage denials) and a product asset.

### 1.1 What the assignment actually says

From `case-study-prompt.pdf`, verbatim:

> Build a chatbot that Clover Health members can talk to. The goal: reduce the number of calls to our customer service team.

> When they have questions - about their benefits, their providers, a claim, a prior authorization - most of them call us. We want to change that.

**Four named call drivers: benefits, providers, a claim, a prior authorization.** Two of them are answerable from public plan documents. The other two require knowing who the member is. A public-documents-only product addresses half the problem as the assignment states it. This is the reason the authenticated features sit in P2 (P2-15 through P2-20) rather than the optional tier.

The assignment also states what is **not** being assessed: healthcare domain expertise, production-quality code, visual design polish, or adherence to any framework. What is assessed is "how you think, how you build, and how you handle a messy, real-world problem," across a 60-minute interview of which ~45 minutes is dialogue. That ratio means the recorded reasoning - section 9 of this document, and `claude/design-decisions.md` - is a first-class deliverable, not documentation of one.

## 2. Why the priorities are ordered the way they are

A call is deflected only if every one of these holds:

| Step | Condition                                                            | Where it is addressed                                             |
| ---- | -------------------------------------------------------------------- | ----------------------------------------------------------------- |
| 1    | Member finds the assistant                                           | P1-05 launcher, P2-12                                             |
| 2    | Member trusts it enough to type instead of dial                      | P1-03 citations, P1-09 scope disclosure, P1-08 visible human path |
| 3    | Correct chunk retrieved from correct document                        | P1-01, P1-02, P2-09                                               |
| 4    | Answer is correct and complete enough they do not re-verify by phone | P1-03, P1-04 plan context, P1-11 eval                             |
| 5    | Member can read and understand it                                    | P1-06 accessibility, P2-08 answer format                          |
| 6    | On failure, handoff does not create a worse call                     | P1-08 escalation                                                  |

Anything that does not touch a step above is decoration. That test decides every placement below.

Two consequences worth stating up front. **Step 2 is the choke point, not step 3** - a technically excellent retriever that members do not trust deflects nothing. And **a wrong answer is worse than a refusal**, because it generates the original call plus a complaint call. Refusal quality is therefore a P1 concern, not a fallback.

## 3. Locked decisions

| Decision         | Value                                                                                            |
| ---------------- | ------------------------------------------------------------------------------------------------ |
| Success metric   | Call deflection (volume)                                                                         |
| Channel          | Web chat on cloverhealth.com only                                                                |
| Corpus scope     | One plan, deep: 2026 Clover PPO, one state                                                       |
| Generation model | Azure OpenAI gpt-4o, API version `2025-01-01-preview`                                            |
| Embeddings       | Azure OpenAI `text-embedding-3-small`, same resource. Stack is all-Azure.                        |
| Vector store     | Supabase Postgres, pgvector HNSW + `tsvector` GIN, RRF fusion in an RPC                          |
| Hosting          | Vercel                                                                                           |
| Voice input      | ElevenLabs Scribe v2 Realtime (WebSocket), Fish Audio fallback                                   |
| Voice output     | ElevenLabs Flash v2.5 (`eleven_flash_v2_5`), Fish Audio fallback, native `speechSynthesis` floor |
| Auth (P2)        | Email 6-digit OTP via Resend, session bound to a member row                                      |
| Member data (P2) | 5 seeded synthetic members. No real PHI at any point.                                            |
| Escalation       | Pre-filled callback form primary, phone number always visible                                    |
| Landing page     | Clover-faithful, with an unaffiliated-case-study disclaimer                                      |
| Cost             | $0. Free tier, open source, or already-owned infrastructure.                                     |

**P1 and P2 are mandatory. P3 and P4 ship if time permits.**

## 4. Architecture at a glance

```
cloverhealth.com shell (Next.js on Vercel)
  └── launcher, bottom right
       └── panel, 40% viewport right, or fullscreen route
            └── /api/chat  (streaming)
                 ├── query rewrite            gpt-4o
                 ├── hybrid retrieve          Supabase RPC: pgvector HNSW + tsvector, RRF k=60
                 ├── rerank                   P2
                 ├── confidence gate          cite or refuse, no third path
                 ├── generate                 gpt-4o, streaming
                 └── log                      question, chunks, answered|refused, feedback

Voice mode (P2)
  mic, press-and-hold or tap-to-toggle
    → ElevenLabs Scribe v2 Realtime, WebSocket
         partial_transcript  → rendered live under the mic
         committed_transcript → editable, then sent to /api/chat
    → answer text streams to the panel AND to TTS
         ElevenLabs Flash v2.5 → Fish Audio → native speechSynthesis
         cached in Supabase Storage, keyed on hash(answer text + voice id)

Corpus build (offline, versioned)
  EOC / Summary of Benefits / formulary / provider directory
    → markdown → header chunking → contextual prefix → embed → Supabase

Authenticated tier (P2)
  Resend OTP → session → scoped member record → member-specific answer + audit log

Member document upload (P4, requires a session)
  upload → type/size gate → parse → chunk → embed → store scoped to that member
    → retrievable alongside plan documents, cited by filename and page
    → member-visible list, deletable, auto-purged on a retention timer
```

## 6. P2 - Deflection amplifiers

Mandatory. Each one raises a specific step of the funnel on top of a working spine.

**P2-15 through P2-20 are the authenticated member tier**, moved up from P3 because section 1.1 names a claim and a prior authorization as two of the four things members call about. Without them the product answers half the stated problem. The security hardening that would accompany them in production stays in section 7.

**These records are synthetic.** Five seeded fictional members. No real PHI touches this system at any point, which removes the HIPAA problem entirely while still allowing the real access patterns to be built and demonstrated.

## 7. P3 - Hardening the authenticated tier

Optional, ships if time permits. The authenticated feature set moved to P2-15 through P2-20; what remains here is the security work that would sit underneath it in production.

**Framing that must survive into the SRS:** the 5 member records are synthetic, so nothing here is protecting real data. Building these controls against synthetic data is still the strongest available version of the argument - it shows the production requirements are understood without a covered entity's data ever being involved.

| ID    | Item                                                                                                                                                                                                                                                                                                                      | Notes                                                                                                                                                                                                                               | Effort |
| ----- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------ |
| P3-01 | **Database-level access control and audit.** Row-Level Security scoping every member row to its session, replacing the application-layer scoping P2-19 ships with. Audit log of every authenticated answer: who, what was asked, which fields were read, when. Minimum-necessary field access. Re-auth on session expiry. | The controls are the deliverable more than the feature. This is the section a Clover engineer actually reads, and it is the difference between "I built a login" and "I understand why payers build logins the way they do."        | L      |
| P3-02 | **The real-PHI writeup.** What changes when the data stops being synthetic: BAA-eligible model tier, zero-data-retention configuration, encryption in transit and at rest, RBAC, disclosure accounting, retention policy, incident response.                                                                              | Written, not built. Converts "I used fake data" from a limitation into demonstrated understanding of the real requirements. Cheap, and it directly answers the "what if X happened" line of questioning the assignment warns about. | S      |

A tour a member cannot re-run is a tour they have effectively never seen.                                                                          | M      |
| P4-07 | **Member document upload.** Available only inside an authenticated session (requires P2-16). Member uploads a PDF or Word file - an EOB, a bill, a letter - which is parsed, chunked, embedded, and stored scoped to that member. Real deflection value: "what is this letter telling me?" is a call, and it is one the plan corpus alone cannot answer. See the four build conditions below the table - they are what make this safe to ship publicly rather than optional polish. | L      |

**P4-07 ships only with all four of these:**

1. **The coverage-determination boundary still binds.** A member uploading a denial letter will ask "is this right?" The bot explains what the document says and how the appeal and grievance process works. It does not judge whether the denial was correct. This is P1-10 extended to a new input, and it is the specific risk this feature carries.
2. **An uploaded file is untrusted input entering the model context.** Prompt injection through a crafted PDF is a real path to making the bot ignore its citation rules. Content from uploads is fenced and labeled as member-supplied in the prompt, never as instructions, and the P1-11 eval harness gets an injection case built from a hostile upload.
3. **Type allowlist, size cap, page cap, and per-session upload limit.** Parsing arbitrary user files is where file-handling bugs live.
4. **A plain-language warning plus real deletion.** The deploy is public, the accounts are synthetic, but the files people upload will be real. Tell members not to upload documents they would not want stored, purge on a timer, and make delete actually delete rather than hide.

## 9. Cut, with reasons

Each of these was considered and rejected. The reasoning belongs in the SRS non-goals, because a well-argued cut is worth more than a marginal feature.

| Item                                                      | Why cut                                                                                                                                                                                                                                                                                                                                                                                                                      |
| --------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Keyboard shortcut labels on elements ("Ctrl+Shift+V")** | Phone users have no keyboard. Desktop seniors overwhelmingly do not use chords. The accessibility population that does use keyboards is screen-reader users, and JAWS and NVDA already claim most Ctrl+Shift combinations, so a custom chord collides. Printed chord labels are visual noise on a screen where contrast budget matters. The useful subset - Tab reaches everything, Esc closes, visible focus - is in P1-06. |
| **In-app font-size controls**                             | 18px base type with correct reflow at 200% zoom (WCAG 1.4.4, required anyway) makes the control redundant. Browser and OS zoom already do this, system-wide, in a way the member has already configured.                                                                                                                                                                                                                     |
| **Agent-assist console, IVR interception, SMS**           | Higher-leverage than web chat at Clover's actual scale - the call volume is on the phone, and agent-assist touches every call rather than a fraction. Deliberately out of scope for this product, which is web-only by decision. Worth naming in the SRS as the obvious next channel.                                                                                                                                        |

## 10. Case study deliverables

Not product features. Tracked separately so they do not compete with P1. The assignment sets no required output format, and ~45 of the 60 interview minutes are dialogue, so these are weighted for that.

- **The reasoning record.** `claude/design-decisions.md` plus section 9 of this document. Every fork, the options, the choice, the cost accepted. This is the artifact the 45-minute dialogue actually runs on, and the assignment says explicitly that it is testing how you think and how you handle ambiguity. Highest-value deliverable here, above the demo.
- **A live walkthrough.** The assignment prefers "a rough prototype or interactive walkthrough" over a polished deck, and states that visual design polish is not assessed. Ten minutes, built around three questions the assistant answers perfectly, chosen in advance and worked backward from.
